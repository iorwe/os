## 实现的功能

- 实现了一个任务同步机制，主要包含两种互斥锁（自旋锁和阻塞式互斥锁）和信号量。
- 自旋锁通过循环尝试获取锁，若锁被占用则挂起当前任务；阻塞式互斥锁则将任务加入等待队列并阻塞，直到锁可用。
- 信号量支持 up 和 down 操作，分别用于增加和减少信号量计数，并管理等待任务。
- 任务控制块（TaskControlBlock）管理单个任务的所有信息，包括所属进程、内核栈、任务状态、互斥锁和信号量状态等。
- 通过 MutexStatus 和 SemaphoreStatus 结构体记录任务对互斥锁和信号量的分配和需求状态，确保任务能正确管理同步资源。
- 在锁或信号量资源不足时，任务会被阻塞或挂起，让出 CPU 给其他任务；当资源可用时，会唤醒等待的任务，确保任务能继续执行。

## 简答题

### 1

#### 需要回收的资源

- 用户态资源：包括用户栈、用户态页表等，这些资源在 TaskUserRes 中管理。
- 内核栈：每个线程的内核栈需要被回收。
- 任务控制块（TaskControlBlock）：包括任务状态、互斥锁和信号量状态等。
- 进程控制块（ProcessControlBlock）：包括进程状态、任务列表等。

#### TaskControlBlock 可能被引用的位置及回收情况

1. 进程控制块（ProcessControlBlock）中的任务列表：

- 进程控制块中维护了一个任务列表，存储了所有线程的 TaskControlBlock 引用。

- 当主线程退出时，需要遍历该列表，结束所有线程并回收其资源。

- 需要回收，因为任务列表是进程管理线程的主要数据结构，必须清理以避免内存泄漏。

2. 调度器中的任务队列：

- 调度器可能将 TaskControlBlock 放入就绪队列或阻塞队列中。

- 当主线程退出时，需要从调度器中移除所有相关线程的 TaskControlBlock。

- 需要回收，因为调度器中的引用会影响线程的调度状态，必须清理以确保调度器正常工作。

3. 互斥锁和信号量的等待队列：

- 互斥锁和信号量的等待队列中可能存储了等待资源的线程的 TaskControlBlock 引用。

- 当主线程退出时，需要清空这些等待队列，并结束相关线程。

- 需要回收，因为等待队列中的引用会导致线程无法被正确唤醒，必须清理以避免死锁。

4. 其他线程的 TaskControlBlock 引用：

- 其他线程可能通过 Arc 引用 TaskControlBlock，例如在任务协作或资源共享时。

- 当主线程退出时，需要确保这些引用被正确释放。

- 需要回收，因为 Arc 引用会导致 TaskControlBlock 无法被正确释放，必须清理以避免内存泄漏。

### 2

#### 区别总结

1. `lock` 方法的处理方式:
   - `Mutex1` 的 `lock` 方法会 **循环尝试** 获取锁，直到成功。这意味着即使被唤醒的任务，如果再次检查时锁仍然被占用，它会再次进入等待队列并阻塞。
   - `Mutex2` 的 `lock` 方法只 **尝试一次**。如果锁被占用，它会阻塞；如果被唤醒，它会直接返回，假设它现在拥有锁（因为 `else` 分支直接设置 `locked = true`）。
2. `unlock` 方法中 `locked` 状态的更新时机:
   - `Mutex1` 的 `unlock` 方法在释放锁时，**总是**将 `mutex_inner.locked` 设置为 `false`。
   - `Mutex2` 的 `unlock` 方法只有在 **没有等待任务** 时，才将 `mutex_inner.locked` 设置为 `false`。如果 `wait_queue` 不为空，它会唤醒一个任务，但 `locked` 状态会保持 `true`。

#### `Mutex2` 的实现存在问题，可能导致以下情况：

1. **死锁 (Deadlock):**
   - 考虑以下场景：
     1. Task A 调用 `mutex2.lock()`。假设锁当前未被持有，Task A 成功获取锁，`mutex_inner.locked = true`。
     2. Task A 调用 `mutex2.unlock()`。假设 `wait_queue` 为空，`mutex_inner.locked` 被设置为 `false`。一切正常。
     3. 现在，Task A 调用 `mutex2.lock()`。假设锁未被持有，Task A 再次成功获取锁，`mutex_inner.locked = true`。
     4. 此时，Task B 调用 `mutex2.lock()`。因为 `mutex_inner.locked` 是 `true`，Task B 被加入 `wait_queue`，然后阻塞。
     5. Task A 调用 `mutex2.unlock()`。`wait_queue` 不为空（Task B 在里面），所以 Task B 被唤醒，但是 `mutex_inner.locked` **仍然保持 `true`**。Task A 也继续执行。
     6. 现在，Task A 尝试再次调用 `mutex2.lock()`。它会看到 `mutex_inner.locked` 仍然是 `true`，因此它会把自己加入 `wait_queue` 并阻塞。
     7. Task B 被唤醒，它从 `block_current_and_run_next()` 返回。它会继续执行 `Mutex2::lock` 方法中 `if mutex_inner.locked` 的 `else` 分支。**它不会重新检查 `mutex_inner.locked`**，而是直接设置 `mutex_inner.locked = true` (这行代码是冗余的，因为前面已经为 true)。它现在认为自己拥有锁。
     8. **问题：** `mutex_inner.locked` 状态一直是 `true`。Task A 和 Task B 都认为自己拥有锁，或者说 `locked` 状态一直没被正确重置为 `false`。
     9. 如果 Task B 尝试调用 `mutex2.unlock()`，它会唤醒 Task A，但 `locked` 状态仍然保持 `true`。
     10. **最终结果：** 除非 `wait_queue` 最终为空，否则 `locked` 状态永远不会变为 `false`。即使 `wait_queue` 为空，也只有在最后一次 `unlock` 时才会将 `locked` 设置为 `false`。这会导致在有任务等待的情况下，`locked` 状态无法正确反映锁的真实持有情况，从而可能导致多个任务同时进入临界区，或者在没有任务持有时锁仍然显示为已锁定的状态，最终导致死锁。
2. **数据竞争 (Race Conditions):**
   - 由于 `Mutex2` 在 `unlock` 时，当有等待任务时，`mutex_inner.locked` 保持 `true`，并且唤醒的任务在 `lock` 方法中不会重新检查 `locked` 状态，这可能导致多个任务都错误地认为自己获得了锁，从而同时进入临界区，引发数据竞争。
3. **不公平性 (Unfairness) / 活锁 (Livelock):**
   - 在 `Mutex2` 中，当一个任务被唤醒时，它并不会再次检查锁的状态。这可能导致一些任务在被唤醒后，立即被另一个任务抢占并再次尝试获取锁，而之前的任务可能永远无法成功获取锁。虽然不直接是活锁，但这种行为可能导致任务长时间无法获取锁。
