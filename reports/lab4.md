## 实现的功能

### 1. 硬链接（linkat）

*   功能：实现了 sys\_linkat 系统调用，可以为一个已存在的文件创建一个新的硬链接（即不同的目录项指向同一个 inode/磁盘块）。
    *   通过 link\_at 方法，在目录下为 old\_name 文件创建名为 new\_name 的新目录项，且新旧目录项的 inode id 相同。
    *   忽略了 olddirfd、newdirfd 和 flags 参数，仅处理路径。
    *   如果新文件名已存在，则返回错误。


* * *

### 2\. 取消链接（unlinkat）

*   功能：实现了 sys\_unlinkat 系统调用，可以删除一个文件路径到文件的链接。
    *   通过 unlink\_at 方法，删除指定名称的目录项。
    *   如果该文件的所有硬链接都被删除，则回收对应的 inode 及其数据块，实现了文件的彻底删除。
    *   忽略了 dirfd 和 flags 参数，仅处理路径。
    *   文件不存在时返回错误。


* * *

### 3\. 获取文件状态（fstat）

*   功能：实现了 sys\_fstat 系统调用，可以获取文件的详细状态信息。
    *   通过 get\_fstat 方法，获取指定文件的 inode id 及硬链接数量。
    *   填充 Stat 结构体，包括设备号（固定为 0）、inode 编号、文件类型（普通文件或目录）、硬链接数量等。
    *   支持通过文件描述符获取文件状态。

## 简答题

### 1

#### Root Inode 的作用

easy-fs 是一个扁平化 (flat) 的文件系统，它的结构非常简单

- 唯一的目录：整个文件系统只有一个目录是根目录，由 ROOT_INODE 代表。

- 直接的父子关系：所有的文件都直接存储在根目录下，它们的目录项都记录在 ROOT_INODE 指向的数据块中。

- 因此，执行以下操作时，ROOT_INODE 是直接的操作对象：

  - 打开文件 (open)：需要在 ROOT_INODE 下查找文件的目录项以获取其 inode。

  - 创建硬链接 (linkat)：在 ROOT_INODE 下添加一个新的目录项，指向一个已存在的 inode。

  - 取消硬链接/删除文件 (unlinkat)：从 ROOT_INODE 下移除一个目录项。

  - 获取文件状态 (fstat)：首先需要在 ROOT_INODE 下找到文件的目录项，然后获取其 inode 信息。

#### Root Inode 损坏的后果

- 无法找到任何文件：由于 ROOT_INODE 是查找所有文件的唯一入口点，一旦它损坏，文件系统就失去了定位任何文件 inode 的能力。无法打开、读取、写入或执行任何文件，因为系统根本不知道这些文件在哪里。

- 无法列出根目录内容：ls / 或类似操作会失败，因为无法读取或解析 ROOT_INODE 的数据块来获取文件列表。

- 整个文件系统瘫痪：由于只有一个目录（根目录），且它是所有文件的容器，ROOT_INODE 的损坏直接导致整个 easy-fs 文件系统完全无法使用。

### 2

在 Linux 终端中，管道（pipe）常用于将一个程序的输出直接作为另一个程序的输入。例如：

```bash
cat file.txt | wc -l
```

这个命令的作用是统计 file.txt 文件的行数。其原理如下：

*   cat file.txt 会把文件内容输出到标准输出（stdout）。

*   | 管道符会把前一个命令的输出连接到下一个命令的输入（stdin）。

*   wc -l 会读取输入流，统计其中的行数。

实际应用场景说明：

1.  cat file.txt 读取文件内容，输出到管道。

1.  管道（pipe）把这些内容传递给 wc -l。

1.  wc -l 统计行数并输出结果。

在代码层面，这背后其实就是父进程创建一个 pipe，然后 fork 出两个子进程，一个执行 cat，一个执行 wc -l，并通过 pipe 连接它们的输入输出。

### 3

提出一个基于 **中央消息代理（Message Broker）** 或 **共享消息总线（Shared Message Bus）** 的设计思路，类似于许多现代消息队列系统或分布式系统中的服务总线概念，但针对单机多进程场景进行简化。

**核心思想：**

不再让进程直接两两通信，而是引入一个中介（可以是专用进程，也可以是内核对象如消息队列，或共享内存区域）。所有进程都与这个中介交互来发送和接收消息。

**设计方案：基于中央消息路由（Broker）模式**

1. **组件:**
   - **消息代理/路由器:** 一个独立的、长期运行的进程。它是通信的核心枢纽。
   - **客户端库 :** 每个需要通信的应用程序进程都会链接或使用这个库。库封装了与 Broker 通信的细节。
   - **通信协议/通道:** 客户端库与 Broker 之间需要一种高效的本地 IPC 机制（例如 Unix Domain Sockets, POSIX 消息队列, 或者基于共享内存+同步机制）。
2. **工作流程:**
   - **启动与注册:**
     - 首先启动 Broker 进程。
     - 每个应用程序进程（称为 Client）在启动时，通过客户端库连接到 Broker。
     - 连接时，Client 可以向 Broker 注册一个唯一的身份标识（例如，进程名、PID 或自定义 ID）。Broker 维护一个当前连接的 Client 列表及其标识。
   - **消息发送:**
     - 当一个 Client (Sender) 想要发送消息给另一个或多个 Client (Receiver) 时，它不直接连接 Receiver。
     - Sender 通过客户端库将消息发送给 Broker，并指定目标：
       - **点对点:** 指定目标 Client 的唯一 ID。
       - **发布/订阅 :** 指定一个 "主题" 或 "频道" 。
       - **广播:** 指定发送给所有当前连接的 Client。
   - **消息路由:**
     - Broker 接收到来自 Sender 的消息。
     - 根据消息中指定的目标信息：
       - **点对点:** Broker 查找目标 ID 对应的 Client 连接，并将消息转发给该 Client。如果目标 Client 不在线或不存在，可以返回错误给 Sender 或将消息缓存（取决于设计）。
       - **发布/订阅:** Broker 查找所有订阅了该 Topic 的 Client，并将消息的副本转发给每一个订阅者。
       - **广播:** Broker 将消息的副本转发给所有当前连接的 Client（可能排除 Sender 自身）。
   - **消息接收:**
     - 每个 Client 通过客户端库监听来自 Broker 的消息。
     - 客户端库通常提供一个阻塞或非阻塞的 receive() 接口。当 Broker 转发消息给某个 Client 时，该 Client 的 receive() 调用会返回收到的消息。
   - **断开连接:**
     - 当 Client 退出时，客户端库应负责通知 Broker 断开连接。
     - Broker 需要优雅地处理 Client 的意外断开，并更新其内部状态（移除 Client 注册信息、清理订阅等）。
